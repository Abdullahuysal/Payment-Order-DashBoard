# Backend — Project Instructions

## Comments

**No narrative comments in backend code.** When writing or editing any file under `backend/`,
do not add comments that explain, restate, or justify what the code does. Remove existing
ones when you touch the surrounding code.

The only comments allowed to stay:

- **XML doc comments** (`/// <summary>`, `<param>`, `<returns>`, `<inheritdoc/>`) on a type
  or member — the "definition summary".
- A **single short line** documenting a non-obvious **configuration value or magic constant**
  (e.g. an odd timeout, a protocol quirk, a required exact string) where deleting the note
  would invite someone to "simplify" it and break behaviour.
- Generated-code markers that tooling owns (`// <auto-generated />`, migration `#pragma`).

Anything else — step-by-step narration, "why we do this", TODOs, commented-out code — is not
allowed. Make the code self-explanatory with names and small methods instead.

## Architecture

See `backend/README.md` ("Project layout" / "Architecture decisions"). In short: vertical
slice under `Features/<Feature>/V<n>/<Operation>/`, one endpoint per folder, shared bits in
`V<n>/Shared/`; endpoints self-register via `IEndpointModule` (never edit `Program.cs` for a
new feature or API version); static handlers take `AppDbContext` / gateway interfaces
directly (no repository or service layer); `record` DTOs, hand-mapped, entities never leave
the API; `TypedResults` + RFC 9457 `ProblemDetails` on every error path. Central Package
Management, warnings-as-errors, `.editorconfig` is authoritative.
